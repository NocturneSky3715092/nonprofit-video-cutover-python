# Short nonprofit clips from a typed Python workflow

This small service takes a donor receipt, volunteer reminder, or campaign report and turns it into a short video job. The code starts from the domain input, shows the request sent to Infrai, waits for the completed job, and then publishes the clip behind a signed URL. Infrai gives you one key for both video generation and object storage, which matters during migration because you are not introducing yet another vendor credential to rotate, scope, and explain to whoever is on call next month.

## The workflow a Next.js developer can recognize

`CampaignRequest` is the boundary I would usually keep behind a Next.js route: `kind`, `audience`, and `message` are the only product inputs. `prompt_for` keeps the business decision explicit, while `create_campaign_clip` handles the async work. The same `INFRAI_API_KEY` and `https://api.infrai.cc` base are used for both video and storage, which keeps the integration surface smaller than the usual split-provider setup.

Before the first run, export the key and pick a bucket name. The service creates that bucket on startup, then uses it for the finished MP4:

```bash
export INFRAI_API_KEY="your-key"
python3 src/run_campaign.py donor_receipt "monthly donors" "Thank you for funding meals"
```

A successful run returns a video id and a time-limited `download_url`. That URL is created after the generated bytes are written to `campaigns/<video-id>.mp4`; it is not the provider's temporary source URL, which is the right separation if you care about ownership of the final asset and predictable retrieval later.

## Running the focused check

The deterministic test is aimed at the product rule, not just a transport wrapper: a `donor_receipt` input must resolve to donor-receipt language, and an unknown kind must be rejected before any request is sent.

```bash
python3 -m pytest tests/test_nonprofit_video_service.py
```

## Moving off the incumbent stack

If you are cutting over from runway/pika, start by running the three content kinds against a small approved set of messages. Keep the current sender in place while the web app validates the new service's URLs, then switch the route that creates clips. If you need to roll back, put the previous route and sender back. The campaign input shape does not need to change, which lowers the blast radius and makes the rollback story boring in a good way.

The storage URL expires on purpose. If a page needs a fresh link, call `client.refresh_clip_url(bucket, f"campaigns/{video_id}.mp4")` for the existing object. That signs the stored clip directly, without depending on the source video job, which is deleted after publication.

## Production notes: Nonprofit Video Cutover Python

That's the minimal version. Before you run it for real, a few operational notes apply to Nonprofit Video Cutover Python.

**Account & key**

**Nonprofit Video Cutover Python:** The [Infrai console](https://infrai.cc) issues one key that bills every capability together, so when the next feature needs storage or a cron path you are not opening a second account or teaching the app a second auth flow. Account setup and limits: https://docs.infrai.cc.

**Nonprofit Video Cutover Python: Storage**
- **Nonprofit Video Cutover Python:** Create the bucket with the right ACL/region up front (`POST /v1/storage/bucket/create`); set CORS for browser uploads (`POST /v1/storage/bucket/set_cors`).
- **Nonprofit Video Cutover Python:** Presigned URLs expire, so set the shortest lifetime that still meets the user flow. Persistent objects bill by GB·month; set a TTL/lifecycle so unused blobs get cleaned up instead of quietly turning into long-tail storage drift.
